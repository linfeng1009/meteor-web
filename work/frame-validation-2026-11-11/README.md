# 前台帧率复核（2026-11-11）

## 本轮计划与结果

按静止、持续转视角、边移动边出招分别测量真实WebGL画面的RAF帧间隔、P95/P99、最大帧和CPU分段耗时；再检查高清人物、不同地图、不同视口和实际锁定鼠标输入。完成自动回归后提交推送当前功能分支，保留现有PR待审核。

本轮扩展了诊断页和自动测试，没有从这些数据发现需要继续修改游戏渲染循环的瓶颈。新增测量完整保留长帧，修复了原诊断页可能把后台限速、尺寸变化、零有效鼠标输入误判为有效采样的问题。

## 可复现的自动转向结果

使用本机应用内浏览器、WebGL真实渲染、高画质、原版长剑、三名对手，关闭自动倍率，避免用降分辨率掩盖掉帧。每项重新开局，预热3秒、采样10秒。自动转向调用与鼠标相同的角度函数；移动出招通过游戏action入口执行。AI和碰撞照常运行，角色可能因受击和身体分离移动。

| 1280×720 / 春田 / 四方阵 | 60.00 | 60.00 | 60.00 | 16.8ms | 0 |

原始JSON与本文件同目录。12项共约120秒采样；最大帧23ms。炎硫岛八重神子持续转向的镜头CPU均值约0.156ms，整帧CPU约5.42ms，移动出招约7.01ms。没有复现“仅转向就掉帧”的情况。

这些是**视口尺寸**，不是全屏绘制缓冲大小。诊断页画布高70vh：1280组绘制缓冲约1920×756（DPR1.5），1920组为1905×756（DPR1）。原始JSON记录实际画布及buffer，不能将结果宣称为1920×1080全屏渲染、144Hz显示器或所有硬件均稳定60FPS。前两组采用修复滚动条前的页面，CSS画布宽度在输出结果后有15px变化，绘制缓冲保持不变；后两组已预留滚动条。

## 鼠标实测的边界

尝试锁定鼠标并通过浏览器输入操作移动视角，最终记录见 `yaemiko-manual-rejected.json`：30秒约60FPS、无25ms长帧，但锁定鼠标事件为0，视角变化为0，并捕获三次“鼠标锁定未成功”提示。因此**真实锁定鼠标输入验收未通过**，这30秒不能当作鼠标转向不卡顿的证据。未绕过浏览器的指针锁定限制，也没有用脚本伪造锁定成功。

另发现应用窗口最小化时，即使页面报告visible，也可能被限速为约1FPS；恢复应用后恢复60FPS。`viewport-throttled-manual.json`和`manual-unverified.json`保留早期无效实验，旧版validForComparison标记存在缺陷，不能按该旧标记采信。当前判定要求复核500ms以上停顿、隐藏/尺寸变化，并要求鼠标锁定事件及累计视角变化都存在。所有长帧仍保留在数值统计中，不做剔除。

当前证据能支持自动持续转向与移动出招的渲染帧率正常，尚不能支持物理鼠标高轮询率、真实浏览器指针锁定或端到端输入延迟已经验收。后续应在用户日常Chrome前台运行诊断页的鼠标实测，确认lockedEvents、angleTravel和turnFrames有数值，并结合FPS/P95复核；自动与实际输入测试明确分开。

## 使用和回归

打开 `/performance-lab.html`，选择人物/地图，运行三项测试，或运行鼠标实测后点“锁定鼠标进行实测”并移动鼠标30秒。界面给出摘要和完整JSON。人工测试不要求最终净旋转不为零，累计往返转动同样有效。该页面不加载用户游戏偏好，也不改联机中继。

新增测试覆盖有限时段统计、长帧保留、P99、无效数据拒绝、背景/变尺寸复核和鼠标往返转向验证。

最终回归：529/529项通过，50个运行模块语法检查通过。推送前发现维护者已将PR #2合并（master 0ad2381），因此本轮从该master建立feature/帧率实测验收分支供后续PR审核。其树与已测试基线完全相同，未执行向主分支合并。
