# 联机操作确认与重试

## 问题和协议

旧版中继在房主读取时立即清空队列，房主响应丢失会永久丢失操作；客人端的重试无法覆盖这一段。客户端队列超过63条、中继超过128条也会静默丢弃已接收的动作。

协议第2版增加对局round与确认序号：

1. 客人发送最多64条的有序批次，保存原批次直到收到acceptedSequence确认；请求或响应丢失时用相同序号重试，中继按序号去重。
2. 中继收到后保留操作，不因房主读取而移除。房主请求带上一次成功应用的inputAck；中继只删除已确认操作。房主响应丢失，下次仍可读取。
3. 房主逐条调用实际输入消费者，成功后记录本对局该玩家的序号。重复投递被跳过，确认请求/确认响应丢失可重复提交，不重复执行攻击、跳跃、锁定等动作。
4. 新一局增加round并清空确认状态。旧局写入被拒绝，离房或新局期间迟到的同步响应不再触发旧回调。加载未完成时不确认输入，执行异常明确结束会话，不盲目重放部分执行的批次。

确认意味着输入处理器已成功消费，不意味着招式一定起手/命中；硬直、怒气和连招窗口仍由战斗规则判断。状态保存在内存中，仅保障当前会话内的重试；刷新、进程崩溃和服务器重启后的续局不在本轮范围。

## 有界队列

连续输入分批发送，只有队列已全部进入当前批次时才追加look，避免look的新序号跨过尚未发送的旧操作。客户端与中继最多积压256条；客户端超限明确断开，中继满时拒收新批次但保留已接受的全部操作，下一次可重试。非法批次和非法确认在修改队列前整体校验，未来序号确认及客人伪造房主确认被拒绝。

连续3次网络请求失败仍结束会话；没有增加自动重连或无限重试。房主本地操作不进入客人的发送队列，避免反复打开菜单积压无用clear。客人超时的clear为可重复的释放状态指令，序号0，不属于攻击等可靠动作的确认序列。
